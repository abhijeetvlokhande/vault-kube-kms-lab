Vault KMS for Kubernetes — Lab Overview

What this lab does, how to set it up, and what each scenario demonstrates.
Author: Abhijeet Lokhande (SA APJ)

What it is

This lab shows Vault Enterprise as a Kubernetes KMS v2 provider. When configured, every Kubernetes secret is encrypted before it reaches etcd. The key that encrypts each secret's data encryption key (DEK) never leaves Vault — it lives in the Transit secrets engine. An etcd backup, a stolen disk, or cloud-managed snapshot yields ciphertext only. Reading a secret always goes through the Kubernetes API server, which calls the Vault plugin to decrypt on every read.

The lab uses kind (Kubernetes in Docker) with a single control-plane node, and Vault Enterprise running via Docker Compose on your machine.

Architecture

Setup — one command

1
Install dependencies
bash scripts/install-dependencies.sh
kind, kubectl, go, vault CLI, jq — via Homebrew or apt/dnf.
2
Add your license
cp /path/to/vault.hclic License/vault.hclic
Vault Enterprise license — gitignored, never committed.
3
Bootstrap the full environment
make bootstrap
Starts Vault, configures Transit, creates the kind cluster, builds and deploys the plugin, enables encryption on the API server. ~5–10 min on first run.

The five scenarios

1
Encryption proof
Write a secret via kubectl, then read the raw bytes from etcd using etcdctl. Shows the KMS v2 ciphertext prefix and the complete absence of plaintext in etcd storage.
etcd shows k8s:enc:kms:v2:vault-kube-kms:… — plaintext absent
./vault-demo kms-verify
2
Key rotation
Rotate the Vault Transit master key with one API call. The plugin detects the new key version automatically. Re-encrypt all existing secrets. No API server restart, no application changes.
New key version active — old version retained for decrypt
./vault-demo kms-rotate
3
Vault outage resilience
Stop Vault. Show that existing secrets remain readable (KMS v2 DEK-seed caching in the API server). Show that new writes fail with a 3-second timeout. Restart Vault, unseal, confirm writes succeed again.
Reads survive outage · writes fail · recovery is automatic
./vault-demo kms-failover
4
Observability
Inspect the Vault audit log for encrypt/decrypt entries. Scrape the plugin's Prometheus metrics endpoint (rpc_server_duration_milliseconds). Check /healthz and /readyz.
Every key operation logged in Vault audit · latency visible in metrics
./vault-demo kms-telemetry
5
All scenarios in sequence
Runs kms-setup → kms-verify → kms-rotate → kms-failover → kms-telemetry in order. Use for a full end-to-end walkthrough from a clean bootstrap.
Complete end-to-end demonstration
./vault-demo all

Quick command reference
