The Problem

5 min
"Kubernetes secrets are called secrets, but by default they are not secret at the storage layer. etcd stores them as base64-encoded data. Base64 is encoding, not encryption — anyone with read access to the etcd data directory, an etcd backup file, or a cloud-managed snapshot can decode every secret in the cluster with a single command."
"The Kubernetes API server supports a KMS provider interface. When it is configured, every write to etcd goes through an external key manager. The secret data is encrypted before it reaches storage, and the key never touches etcd or the cluster nodes. That key manager can be Vault."
Background
The encryption uses an envelope model: Kubernetes generates a short-lived Data Encryption Key (DEK) per secret. Vault's Transit engine wraps that DEK with a long-lived Key Encryption Key (KEK). Only the wrapped DEK lands in etcd — the KEK never leaves Vault. Decryption requires both etcd (for the wrapped DEK) and Vault (for the KEK), so neither alone is sufficient.

Vault Side — Transit Key, Policy, AppRole

5 min
"Before we look at etcd, let me show what Vault is doing. We configure three things: a Transit key that acts as the KEK, a minimum-privilege policy that the plugin uses to call Transit, and an AppRole so the plugin can authenticate without a human in the loop."
Walk through (already configured by bootstrap)
# Show the Transit key — the KEK that wraps all Kubernetes DEKs vault read transit/keys/kms # Show the policy — minimum required paths for the plugin vault policy read transit-encrypt-decrypt # Show the AppRole role vault read auth/approle/role/kube-kms
"The policy has four paths: encrypt, decrypt, read the key (for status polling), and sys/license/status so the plugin can verify it is talking to Vault Enterprise. The plugin cannot read or write anything outside Transit."
"The AppRole secret-id lives at /tmp/approle-secret-id inside the kind node, mode 0400. The plugin authenticates once at startup and uses token renewal from that point on. No static credentials sitting in a config file."

The Proof — etcdctl Dump

7 min
"I am going to write a Kubernetes secret — completely normally, the same way any application or developer would. Then I will bypass Kubernetes entirely and read the raw bytes from etcd."
Run
./vault-demo kms-verify
"Look at the raw etcd output. The entry begins with k8s:enc:kms:v2:vault-kube-kms: — that is the KMS v2 ciphertext marker. Everything after it is encrypted data. The plaintext value is not in etcd at all."
What the output means
k8s:enc:kms:v2:vault-kube-kms: — the API server wrote this prefix to mark the entry as KMS v2 encrypted. The bytes that follow are the wrapped DEK seed. To read the secret, Vault must unwrap the DEK. Without Vault, this data is unusable.
"Now watch what happens when I read it back through the Kubernetes API."
Expected question: "Wait — if it's encrypted, how are you reading it as plaintext with kubectl?"
"That is exactly the right question. kubectl get secret goes through the Kubernetes API server — not directly to etcd. When the API server received that read request, it fetched the ciphertext from etcd, then called vault-kube-kms over the Unix socket to decrypt the DEK seed, then used that seed to decrypt the secret data, and only then returned the plaintext to kubectl. The decryption happened inside the API server, on this machine, in real time, by calling Vault. Vault is the only entity that holds the key encryption key. No cloud storage service, no etcd administrator, no one with a copy of the etcd backup can do that — they get the ciphertext. Only a process with valid Vault credentials and the correct policy can trigger that decryption, and every time it happens it is logged in Vault's audit trail."
What to point at on screen
(1) The raw etcd bytes starting with k8s:enc:kms:v2:vault-kube-kms:  ·  (2) The grep showing zero matches for the plaintext value  ·  (3) The kubectl output returning the correct plaintext — decrypted by Vault on this read

Zero-Downtime Key Rotation

6 min
"Key rotation is one of those requirements that sounds straightforward but in practice often means a maintenance window. With Vault Transit and KMS v2, rotation is a single API call. No API server restart. No application downtime. The plugin detects the new key version automatically through the KMS v2 Status RPC."
Run
./vault-demo kms-rotate
"We rotated from version 1 to version 2. min_decryption_version is still 1 — Vault retains the old key version so it can decrypt data written before the rotation. Nothing breaks. Data written before the rotation is still readable. Data written after uses the new key."
Operational note
A typical rotation policy is 90 days. With Vault, that means a cron job runs vault write -f transit/keys/kms/rotate and then kubectl get secrets --all-namespaces -o json | kubectl replace -f -. Zero coordination with Kubernetes operators. The audit log shows exactly when each rotation happened.

Resilience — Vault Outage Behaviour

5 min
"KMS v2 has a specific and well-defined behaviour when Vault is unreachable. Let me show you exactly what happens."
Run
./vault-demo kms-failover
"Vault is stopped. Reading an existing secret succeeds — that is KMS v2's DEK-seed caching. The API server caches the decryption seed in memory after processing each secret. As long as the API server has not restarted, it can serve reads for any secret it has already seen without contacting Vault."
"A write fails with a 3-second timeout. The API server tried to call the plugin to encrypt a new DEK seed, could not reach Vault, and rejected the write rather than storing unencrypted data."
What this means for Vault HA
The HA requirement for Vault in a KMS deployment is write availability, not read availability. Existing secrets remain readable during a Vault outage. Only new writes fail. This is the reason why Vault HA Replication is the right solution for this failure mode.

Observability — Metrics and Audit Log

4 min
"Every encrypt and decrypt the API server performs is logged in Vault's audit log. Let me show two views: the structured audit log and the plugin's Prometheus metrics."
Run
./vault-demo kms-telemetry
"The audit log entries show timestamp, operation, key path, and identity. In production you can enrich the AppRole token with cluster name, namespace, or environment — that context appears in every audit entry."
What rpc_server_duration_milliseconds shows
This is a latency histogram for every KMS v2 gRPC call from the API server to the plugin — how long each encrypt or decrypt round-trip takes. Low values (single-digit milliseconds) indicate a healthy plugin. Latency spikes here mean Vault is slow or the path to it is congested. Scrape this from http://127.0.0.1:9090/metrics inside the kind node.

Production Best Practices

3 min
Rotate the KEK on a schedule
90-day rotation is a common baseline. Vault's auto_rotate_period on the Transit key can automate this without any external scheduler.
Restrict the AppRole secret-id
Set secret_id_num_uses=1 and automate renewal. In production back it with a secrets manager or use Vault Agent.
Use short token TTLs
The lab uses token_ttl=1h. Keep TTLs short and rely on renewal. A compromised token expires quickly.
Deploy Vault HA for write availability
As shown in the resilience scenario: reads survive a Vault outage, writes do not. Vault HA Replication ensures the KMS path stays available.
Enable TLS between plugin and Vault
This lab uses --tls-skip-verify for simplicity. In production the plugin should verify Vault's TLS certificate.
Alert on plugin health endpoints
Scrape /healthz and /readyz (port 8081). A non-200 from /readyz means new secret writes will fail within 3 seconds.
