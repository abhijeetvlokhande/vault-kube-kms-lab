The Problem

5 min
"By default, Kubernetes stores all secrets in a database called etcd. The data is base64-encoded — which just means it's been converted to text. It is not encrypted. Anyone who gets their hands on an etcd backup, a disk snapshot, or even just read access to the etcd data directory can decode every password, token, and certificate in the cluster using a single command. That includes cloud providers, storage admins, and anyone who steals a backup."
"Kubernetes has a built-in way to fix this: you can plug in an external key manager that encrypts every secret before it lands in etcd. Vault is that key manager here. The key that does the encrypting lives inside Vault and never leaves it. So even if someone walks out with the etcd data, all they have is noise."
Simple analogy if needed
Think of it like this: etcd is a filing cabinet. Right now the files inside are just in a foreign language (base64) — anyone who speaks the language can read them. With Vault KMS, the files are locked with a padlock, and Vault is the only place that key exists.

How Vault is Set Up

5 min
"Before we look at the proof, let me show you three things we set up in Vault. First, a Transit key — this is the master key Vault uses to encrypt and decrypt. Second, a policy that limits exactly what the plugin is allowed to do: encrypt, decrypt, and nothing else. Third, an AppRole — a machine credential so the plugin can log in to Vault automatically on startup."
Walk through — already done by bootstrap
# The master key — everything flows through this vault read transit/keys/kms # The policy — plugin can only touch transit/keys/kms vault policy read transit-encrypt-decrypt # The AppRole — how the plugin authenticates vault read auth/approle/role/kube-kms
"The plugin gets a one-time credential at startup and uses token renewal after that. No passwords sitting in config files."
Question: "What if someone steals the AppRole credential?"
"The credential has a short lifespan — one hour in this lab, shorter in production. If it's stolen, an attacker can only use it to call encrypt and decrypt on that one specific key. They can't read the key itself, they can't create new keys, they can't touch anything else in Vault. And every single call they make shows up in the audit log with a timestamp. You'd see it immediately."

Live Proof — etcd Shows Only Ciphertext

7 min
"I'm going to write a Kubernetes secret the normal way — the same command any developer or application would use. Then I'm going to bypass Kubernetes entirely and look directly at what's stored in etcd."
Run
./vault-demo kms-verify
"Look at that raw output from etcd. It starts with k8s:enc:kms:v2:vault-kube-kms: — that's the marker the API server writes to say this entry is encrypted by Vault. Everything after it is scrambled data. The password we just wrote is nowhere in there."
Point at on screen
(1) The raw etcd line starting with k8s:enc:kms:v2:vault-kube-kms:
(2) The confirmation that the plaintext is absent from etcd
(3) The kubectl get secret output returning the correct value — decrypted live by Vault
Question: "If it's encrypted, how does kubectl still return the right value?"
"Great question. When you run kubectl get secret, the request goes to the Kubernetes API server — not directly to etcd. The API server fetches the scrambled data from etcd, then calls the vault-kube-kms plugin over a private socket on the same node, asks Vault to decrypt it, gets the plain value back, and returns it to you. That round trip through Vault happens every single time a secret is read. Every one of those calls is logged. If someone reads a secret at 3am on a Sunday, that's in the audit log."
Question: "Does this slow things down?"
"The plugin runs on the same node as the API server and communicates over a local Unix socket — it's just a file on disk, not a network call. Latency should be in single-digit milliseconds since there's no network involved. We can see the actual numbers in the metrics at the end — keep in mind this is a laptop running everything at once, so don't compare to a production cluster."

Key Rotation — One Command, No Downtime

6 min
"Security policies usually require rotating encryption keys every 90 days. With most systems, key rotation means a maintenance window — you have to re-encrypt everything, coordinate with your Kubernetes team, probably restart something. Here it's one command."
Run
./vault-demo kms-rotate
"We just went from key version 1 to version 2. The API server is running. Applications are running. Nothing was restarted. Vault kept the old key version around so it can still decrypt anything that was written before the rotation. You can run this rotation automatically on a schedule — a cron job, a CI pipeline, whatever fits your workflow."
Question: "What about secrets that were written with the old key?"
"They're still readable. Vault keeps all previous key versions available for decryption. We also re-encrypt all existing secrets as part of the rotation — after that, everything is on the new key. Only then would you tell Vault to retire the old version."

What Happens When Vault Goes Down

5 min
"This is the question everyone asks: what if Vault is unavailable? Let me show you exactly what happens instead of just telling you."
Run
./vault-demo kms-failover
"Vault is stopped. We just read an existing secret — and it worked. The API server keeps recently-used decryption information in memory. As long as the API server hasn't restarted, it can serve reads for secrets it's already seen without contacting Vault."
"Now watch a new write — it fails. The API server tried to contact Vault to encrypt the new data, couldn't reach it after 3 seconds, and refused to store it unencrypted. That's the right behaviour — it would rather fail the write than silently store your password in plaintext."
The key point for the customer
If Vault goes down, your cluster keeps running and existing secrets keep working. Only new secret writes fail. This means Vault's uptime requirement is about write availability — existing workloads are not affected by a brief Vault outage. This is why Vault HA is the right answer for production.
"Now we bring Vault back up, unseal it — and writes immediately start working again. No manual intervention, no plugin restart needed."

Audit Log and Metrics

4 min
"Two quick things here: every encrypt and decrypt operation is in Vault's audit log with a timestamp and the identity that triggered it. And the plugin exposes a metrics endpoint you can scrape with Prometheus."
Run
./vault-demo kms-telemetry
"Each audit log entry tells you when the operation happened, what path it touched, and what authenticated identity called it. In production you'd enrich the AppRole token with metadata — cluster name, environment, team — so the log is even more useful for investigations."
"The metrics show how fast each encrypt and decrypt call is. If those numbers spike, it means Vault is slow or overloaded — you'd get an alert before users notice anything."

What to Do Differently in Production

3 min
Run Vault in HA mode
As the failover demo showed, write availability depends on Vault being up. Deploy Vault with at least 3 nodes and a Raft backend, or use HCP Vault.
Rotate the key on a schedule
90 days is a common baseline. Vault's auto_rotate_period on the Transit key handles this automatically — no external scheduler needed.
Turn on TLS between plugin and Vault
This lab uses --tls-skip-verify for simplicity. In production the plugin should verify Vault's certificate — just point it at your CA file.
Keep the AppRole credential short-lived
The lab uses a 1-hour token. In production use Vault Agent to manage credential renewal so the plugin never holds a long-lived credential.
Alert on the plugin health endpoint
The plugin exposes /readyz on port 8081. If it returns non-200, new secret writes will start failing within 3 seconds. Alert before that happens.
Keep the Vault audit log
Stream it to your SIEM. Every encrypt and decrypt call is there — timestamp, identity, key path. This is your evidence trail for compliance audits.
